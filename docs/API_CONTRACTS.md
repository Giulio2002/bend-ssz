# Public entry points: what each one promises, and what it expects

The library never aborts on a value a caller can build through the checked entry points. The unchecked entry points below are kept because
the proofs and the benchmarks state facts about them; each has a checked counterpart or a stated precondition. Source of the findings:
[docs/CRASH_HUNT.md](CRASH_HUNT.md); the regression run is `tools/crash_hunt/regress.sh`.

| entry point | checked? | contract |
|---|---|---|
| `X_decode_checked(buf, size)` | yes | `None` unless `size <= B.size(buf)`, `size <= 4294967264` (NMAX) and the window lies in the words the buffer's array really holds (`B.Buf` is a public constructor: its size field is a claim, R2-04); otherwise it is `X_decode`. Use this for bytes of unknown origin. Memory (R4-02): the decoded form takes up to about 30 bytes of heap per input byte for the worst shapes (lists of empty variable-size elements: an `ExecutionPayload` of empty transactions, `ProgressiveComplexTestStruct` of empty inner lists), at most `X_dcost(size)` words of 8 bytes for every input (docs/DECODE_AMPLIFICATION.md; a measured estimate, not a proved bound). This entry has no memory limit: a caller whose heap is smaller than that bound for the sizes it accepts must use `X_decode_checked_budget` (opt-in). |
| `X_decode_checked_budget(buf, size, budget)` | yes | `None` (and the buffer; nothing read, nothing allocated) when `X_dcost(size) > budget` or the bound is saturated (`X_dcost(size) = 2^32 - 1`: it does not fit 32 bits, R6-01); otherwise exactly `X_decode_checked(buf, size)` (laws `_decode_vchecked_budget_refuse` / `_agree`). `budget` and `X_dcost` are in heap words of 8 bytes. `X_dcost(size) = ((size >> 3) + 1) * K + 524288`, saturating at 2^32 - 1: K heap bytes per input byte plus a constant 4 MiB. K is the name's entry in codegen/decode_cost.json: MEASURED, not proved (docs/DECODE_AMPLIFICATION.md: ceil(1.25 x the worst density measured over the name's shapes + 1), 0 for a name whose largest encoding fits the constant at 48 bytes per byte), and at least the K of every name nested in it (a block charges at least its body and its payload). Worst K: 40 (ExecutionPayload, BeaconBlockBody, BeaconBlock, SignedBeaconBlock), 31 (ProgressiveComplexTestStruct, ProgressiveTestStruct), at most 7 for every other name. The bound is a MEASURED estimate (K = ceil(1.25 x worst measured density + 1)), not a proved bound. The largest budget, 2^32 - 1, means "up to 2^32 - 2 words" (about 32 GiB), not "no limit": a size whose bound saturates is refused whatever the budget, so an embedder whose heap is 32 GiB or more clamps its budget to 2^32 - 1 and still refuses what does not fit. The bound covers `_decode` alone (R6-02): a caller that then flattens the object (`X_flat`, the Prysm shim's path) needs about 4 more heap bytes per packed input byte (decode + `X_flat`: BeaconState 6.9 per byte against K = 7, DataColumnSidecar 6.1 against K = 6; the dense shapes gain almost nothing: ExecutionPayload of 1-byte transactions 28.8 against 40), and one that dumps it (`X_dump`, one cell per byte) up to about 19 per byte for BeaconState (38.8 for the dense ExecutionPayload shape): such a caller passes a budget with that headroom. The protection is opt-in: only callers of `X_decode_checked_budget` get it; `X_decode_checked` and `X_decode` are unchanged and have no memory limit. The budget covers the decode's own allocations, not the input buffer: an embedder with a fixed heap passes what is left of it after the buffer (the Prysm shim: 8 GiB is 2^30 words). |
| `X_decode(buf, size)` | yes (window) | `None` (and the buffer) unless `size <= B.size(buf)`: the window must lie inside the buffer's size field (a U32 comparison, nothing wraps, no cap on `size`). For a window inside the buffer it validates the bytes of the window (`X_ok`) and reads them; the buffer's size field is a claim (`B.Buf` is a public constructor), so bytes of unknown origin should still go through `X_decode_checked` (storage, CH-05/R2-04). |
| `X_ok(buf, off, len)` | yes | the validator of one window; total for every argument. |
| `X_serialize(o)` | yes | `Encoded{ok, bytes}`: `ok = False` (no bytes) for an object that is not valid (`X_valid`), including a length larger than its storage, a value outside its type, an absent box (CH-12: the size pass keeps the empty box absent, so the checked writer flags it), and an encoding of more than NMAX = 4294967264 bytes (CH-07: the size pass answers the marker 4294967295 for it; `X_valid` answers 0 for the same objects, R4-05). `n * element size` is the checked `O.mulc` and the offset table of a list of variable-size elements the checked `O.mul4c`, so no size wraps (R3-03, R4-03); a union's size adds its selector byte with `O.padd`, so an invalid payload keeps the marker (R4-04). |
| `X_encode(o)` | no | precondition `X_valid(o)`. For an invalid object the size pass answers the marker 4294967295 and `_encode` returns the empty buffer without allocating (CH-02); `_serialize` reports it (`ok = False`). |
| `X_hash_tree_root(h, o)` | no | precondition `X_valid(o)`; it has no error channel (CH-08). The work is bounded by the object's storage: the chunk count is clamped to what the storage holds (CH-03), so a claimed length beyond the storage cannot cost more than the allocation (a list of composites hashes min(n, storage) elements, a cache is allocated at most as deep as its array, R2-03). For a valid object the root is the spec root whatever spare storage it has: storage smaller than the 8 words per chunk the root reads, or bytes past the length in the words up to the end of the last chunk, are cleaned in a copy first (CH-11, R2-02). `X_valid` is 0 for every object of more than NMAX bytes (R4-05: a packed list's length, a list of fixed-size composites' count `floor(NMAX / es)`, a container's or union's total by its size pass), so the precondition excludes them; the clean copy of the root path is sized without the wrap of `n + 31` (R4-01), so even such an object hashes its bytes, not the end of its storage. |
| `X_force(o)`, `X_dump(o, t)` | no | test-oracle helpers: they visit the elements the storage holds (at most the claimed count), so they cost what the storage costs, not what a claim says (R3-02). |
| `X_set` / `X_append` / constructors | yes | return the flag `ok` and the object unchanged when `ok = False`. The cell list (`List[Cell, 4096]`) also refuses a cell whose length is not 2048 bytes (CH-01); every list kind has a count below which its append is accepted: the smaller of its limit and the count whose byte length (and its rounding up to a chunk) does not wrap in U32 (CH-04, R2-01, R2-06), and for a list of fixed-size composites the count whose encoding stays within NMAX = 4294967264 bytes (35,495,597 validators, 22,369,621 pending deposits; the pending partial withdrawals' own limit 134,217,728 is smaller: R3-03, size limit). An append also requires that the object's storage holds the n elements it claims (`O.words_cap` / `Array.size`: R3-02): a claim the storage cannot hold is refused instead of allocating and copying for the claim. The cell setter and appender also refuse a cell whose storage is smaller than 2048 bytes (R2-05). An append into a valid object keeps it valid whatever its spare storage holds: the element that starts a word clears the rest of that word, and the bit that fills bit 31 of a word clears the next word, the delimiter word of the new length (R5-01). |
| `X_default()` | - | a valid object; a vector of variable-size elements holds present default elements (CH-10), so `serialize(default())` is the spec's zero encoding. |
| `X_get(o, i)` / `X_cget(c, i)` | yes | for a list or vector of copyable elements: `Some{element}` and the object unchanged, `None` for `i >= length`. For the nine kinds whose elements are boxed and cannot be copied (`Fulu_list_Attestation_8`, `Fulu_list_Deposit_16`, `Fulu_list_AttesterSlashing_1`, `Fulu_list_ProposerSlashing_16`, `Fulu_list_bytelist_1073741824_1048576` (the transactions), `proglist_VarTestStruct`, `proglist_ProgressiveVarTestStruct`, `proglist_proglist_VarTestStruct`, `vec_VarTestStruct_2`) the getter is `X_take(o, i)` / `X_ctake(c, i)` (R3-01): it MOVES the element out, `Some{element}` and an object whose slot holds the empty box, so the returned list is not valid (`_serialize` refuses it, CH-12) until `_set` puts an element back; `_ctake` marks the slot dirty, so the cached root is the root of the object it returns: an absent box is a zero leaf for the cached and the plain root alike, and it stays absent through both (before crash-fix5 the root put a default element in its place, so a second root, cached or plain, differed). The older name `_get` of these kinds answered the same thing and left a list that looked unchanged. |
| `X_build(buf, size)`, `X_read(buf, off, len)` | no | the second half of `_decode`: precondition `X_ok(buf, off, len)` (CH-09). On bytes that were not validated they can allocate in proportion to a claimed count. They are public symbols only because the decode statements unfold them; call `_decode` or `_decode_checked`. |
| `X_set`, `X_get`, `X_cache_at` on an object whose claim exceeds its storage | no | a hand-built `O.Words{ws, claim}` / `Seq{arr, claim}` that claims more than its array holds is not valid (`X_valid` is 0, `_serialize` refuses it). `X_append` refuses it (R3-02). `X_set` / `X_get` at an index in the claimed range but past the storage answer from the word the index mask selects (aliased storage, a write corrupts another element), and `X_cache_at(arr, n, d)` takes the depth `d` as given (a depth that does not match `n` gives another root; `O.cache_dok` only clamps it to the array): none of these allocates in proportion to the claim or aborts, and no honest object can reach them (R3-04, documented rather than refused: the setter and getter guards are the premises of the read-after-write and root laws of 28 collections). |
| `O.words_blit`, `O.words_slice`, `O.words_resize` | no | `O.*` is the runtime the generated code is written in; its functions assume the representation invariant of `O.Words` / `O.Bits` (storage holds the claimed length). `words_blit` and `words_slice` copy nothing for an empty source (CH-01, R5-02). |

Two limits are part of the contract: a size is a U32 and the value 4294967295 is the invalid marker (the size pass saturates at it), so no object of more than
NMAX = 4294967264 bytes (2^32 - 32: the chunk rounding of the allocation stays below 2^32) is encodable (CH-07, closed by agent/size-limit: it was 2^31 - 1 before);
an element count times a fixed element size is checked (`O.mulc`), so it never wraps (R3-03); `_encode` of an invalid object returns the empty buffer and never
allocates from the marker (CH-02). Lists count in U32, so a list holds at most 2^32 - 2 elements (CH-04). The decode window accepts `size <= 4294967264`.

The proofs do not yet cover the whole accepted range for four types (a documented gap, docs/TRUST.md and
docs/size_limit_statement_diff.md section 4): `X_decode` of `ProgressiveTestStruct` is proved for inputs below 2^31 bytes (`1 + n < 2^31`),
of `ProgressiveComplexTestStruct` below 2^29 (`258 + n < 2^29`), and of `ProgressiveVarTestStruct` and
`ProgressiveSingleListContainerTestStruct` below 2^29 (`n < 2^29`); the decode window facts of the progressive record lists
(`pl_SmallTestStruct`, `l10_*`, `pl_VarTestStruct`, `pl_pl_VarTestStruct`, `pl_ProgressiveVarTestStruct`) hold below 2^31 bytes. Between those
bounds and NMAX the same entry points accept and decode, and that range is checked by execution only (the runtime suites), not by a proof.
